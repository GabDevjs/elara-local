# Contratos Rust ↔ TypeScript

O daemon produz os dados; a janela e o `agent-runtime` os consomem. A struct Rust
que serializa **é** a definição do contrato — o resto é tradução verificada.

Este documento descreve como a tradução funciona, por que existem duas
representações do mesmo tipo em TypeScript, e o que fazer quando um tipo muda.

## O fluxo

```
crates/hardware/src/types.rs          ← fonte da verdade
crates/telemetry/src/types.rs
crates/agentd/src/api/types.rs
        │
        │  #[derive(TS)] #[ts(export, export_to = "…/packages/schemas/src/generated/")]
        │  pnpm bindings  ==  cargo test --workspace export_bindings
        ▼
packages/schemas/src/generated/*.ts   ← 46 arquivos, commitados, nunca editados à mão
        │
        │  import type { HardwareProfile } from './generated/HardwareProfile.js'
        ▼
packages/schemas/src/{hardware,telemetry,api}.ts
        │
        │  HardwareProfileSchema        ← zod, escrito à mão
        │  assertSchemaMatches<HardwareProfile, z.infer<typeof HardwareProfileSchema>>()
        ▼
parseOrThrow(Schema, corpoDaResposta, 'GET /v1/hardware')   ← a fronteira IPC
```

Um arquivo gerado é um alias de tipo e nada mais:

```ts
// This file was generated by [ts-rs]. Do not edit this file manually.

/**
 * Tamanhos de cache por nível, em KiB, agregados por socket.
 */
export type CpuCache = {
  l1dKb: number | null;
  l1iKb: number | null;
  l2Kb: number | null;
  l3Kb: number | null;
};
```

A documentação `///` do Rust vem junto: o desenvolvedor TypeScript lê o mesmo
texto que o desenvolvedor Rust escreveu, sem ninguém ter reescrito nada.

## Por que duas representações

Porque tipos TypeScript **não existem em runtime**.

O corpo que chega pelo socket é `unknown`. Um `as HardwareProfile` faz o
compilador aceitar e não verifica coisa alguma: um daemon de outra versão produz
`undefined` num campo qualquer, e o erro aparece três camadas acima, sem pista da
origem. Um `NaN` numa barra de progresso é o sintoma; a causa é um campo
renomeado a dez arquivos de distância.

Daí a divisão de trabalho:

| Camada      | Existe em  | Responde por                             |
| ----------- | ---------- | ---------------------------------------- |
| tipo gerado | compilação | "o campo se chama assim e tem este tipo" |
| schema zod  | runtime    | "o que chegou realmente tem essa forma"  |

Só que agora há duas descrições da mesma coisa — e duas descrições divergem
silenciosamente, a menos que alguém compare. É o que `assertSchemaMatches` faz:

```ts
export const CpuCacheSchema = z.object({
  l1dKb: u32.nullable(),
  l1iKb: u32.nullable(),
  l2Kb: u32.nullable(),
  l3Kb: u32.nullable(),
});
assertSchemaMatches<CpuCache, z.infer<typeof CpuCacheSchema>>();
```

A asserção fica **ao lado** da definição do schema, para que a mensagem de erro
do TypeScript aponte o schema culpado. Ela usa a comparação por identidade de
tipos condicionais (`(<T>() => T extends A ? 1 : 2) extends …`), que — ao
contrário de `extends` — distingue `any`, opcionalidade e ordem de união.

São 46 asserções, uma por tipo gerado. Nenhuma pulada, nenhum `z.any()`.

## Convenções da tradução

| Rust                                 | TypeScript gerado                | Schema zod                          |
| ------------------------------------ | -------------------------------- | ----------------------------------- |
| `#[serde(rename_all = "camelCase")]` | `vramTotalMb`                    | mesma chave                         |
| `Option<T>`                          | `T \| null` (chave **presente**) | `.nullable()`, nunca `.optional()`  |
| `u32`                                | `number`                         | `z.int().min(0).max(4294967295)`    |
| `u64`                                | `bigint`                         | `u64` (aceita number/bigint/string) |
| `f32`, `f64`                         | `number`                         | `z.number()`                        |
| `jiff::Timestamp` (`#[ts(type)]`)    | `string`                         | `z.iso.datetime({ offset: true })`  |
| `[f64; 3]`                           | `[number, number, number]`       | `z.tuple([f64, f64, f64])`          |
| enum unitário `rename_all`           | união de literais                | `z.enum([...])`                     |
| enum com dados `#[serde(tag)]`       | união discriminada por `type`    | `z.discriminatedUnion('type', […])` |

Duas escolhas que não são óbvias:

- **`Option<T>` vira `.nullable()`, nunca `.optional()`.** O serde emite a chave
  com `null`; aceitar a ausência deixaria passar um payload em que o daemon
  simplesmente esqueceu o campo — exatamente o bug que a validação existe para
  pegar.
- **`u64` vira `bigint` e o schema converte.** É decisão do `ts-rs`, não do
  projeto. `JSON.parse` entrega `number`, então o schema `u64` aceita `number`,
  `bigint` ou texto decimal e normaliza para `bigint`. Valores acima de
  `Number.MAX_SAFE_INTEGER` são **rejeitados**, não arredondados: depois do
  `JSON.parse` o dígito já se perdeu, e converter inventaria um valor plausível
  porém errado. Consequência: **corpos de requisição não podem conter `u64`**,
  porque `JSON.stringify` lança em `bigint`.

## Duas peças de configuração que não são opcionais

**`.cargo/config.toml` define `TS_RS_IMPORT_EXTENSION=js`.** Sem ela o `ts-rs`
emite `from "./CpuCache"` e o `tsc` rejeita **todos** os arquivos gerados: o
repositório compila com `moduleResolution: NodeNext`, que exige extensão
explícita em import relativo. A variável fica no `.cargo` e não no script
`pnpm bindings` porque um `cargo test --workspace` sozinho já reexporta as
bindings — se ela dependesse do pnpm, rodar os testes Rust diretamente quebraria
o build do TypeScript em silêncio.

**O `export_to` tem três níveis de `../`.** O caminho do `ts-rs` é relativo a
`<crate>/bindings/`, que é o `TS_RS_EXPORT_DIR` padrão. Logo
`crates/hardware/bindings/../../../packages/…` é a raiz do repositório. Com dois
níveis os arquivos vão parar em `crates/packages/schemas/…`, fora do lugar, e
nada avisa.

## As bindings são commitadas

`packages/schemas/src/generated/` está versionado no repositório e listado no
`.prettierignore`: nenhum formatador toca em arquivo gerado, senão o
`bindings:check` acusaria defasagem a cada `pnpm format`.

Elas são commitadas para que o build de TypeScript não exija a toolchain Rust.
Isso só é seguro se alguém verificar que continuam correspondendo à fonte, e é o
que `pnpm bindings:check` faz em CI: copia o diretório, roda `pnpm bindings`,
compara arquivo a arquivo e falha listando o que mudou.

```
✗ bindings defasadas:
    ~ CpuCache.ts (mudou)
    + NovoTipo.ts (novo)

  Rode pnpm bindings e commite o resultado.
```

## Procedimento: mudar um tipo existente

1. **Edite a struct Rust** no arquivo de contrato
   (`crates/hardware/src/types.rs`, `crates/telemetry/src/types.rs` ou
   `crates/agentd/src/api/types.rs`).

2. **Garanta que o workspace compila** antes de gerar:

   ```sh
   cargo check --workspace
   ```

   Isto não é zelo: `pnpm bindings` **apaga o diretório de saída antes de
   regenerar**. Se um crate não compilar, os tipos dele desaparecem e o build de
   TypeScript quebra com um erro que não se parece com a causa.

3. **Regenere:**

   ```sh
   pnpm bindings
   ```

4. **Rode o typecheck.** Ele vai falhar — é para isso que a asserção existe:

   ```sh
   pnpm typecheck
   ```

   A falha é uma chamada de `assertSchemaMatches` a que passou a faltar um
   argumento: quando os dois tipos divergem, a assinatura passa a exigir um
   parâmetro do tipo `ContractMismatch<Gerado, Inferido>`, cujo campo `__error`
   carrega a instrução ("Schema zod divergiu do tipo gerado do Rust. Rode
   `pnpm bindings` e ajuste o schema"). Como a chamada fica imediatamente abaixo
   do schema, o arquivo e a linha do erro apontam o schema culpado, e a mensagem
   do compilador imprime os dois tipos lado a lado.

5. **Ajuste o schema zod** para acompanhar. O Rust é a fonte; o schema segue,
   nunca o contrário.

6. **Verifique tudo:**

   ```sh
   pnpm typecheck && pnpm test && cargo test --workspace
   ```

7. **Commite os arquivos gerados junto com a mudança do Rust.** Separados, o
   `bindings:check` acusa a defasagem no primeiro commit.

## Procedimento: adicionar um tipo novo

1. Derive `TS` e exporte, no arquivo de contrato:

   ```rust
   #[derive(Debug, Clone, PartialEq, Serialize, Deserialize, TS)]
   #[serde(rename_all = "camelCase")]
   #[ts(export, export_to = ts_export!())]
   pub struct MinhaCoisa { /* … */ }
   ```

2. `pnpm bindings`.

3. Reexporte o tipo em `packages/schemas/src/index.ts`, na seção do crate de
   origem.

4. Escreva o schema zod no arquivo correspondente
   (`hardware.ts`, `telemetry.ts` ou `api.ts`) e **a asserção logo abaixo**. Sem
   a asserção, o tipo entra sem rede de proteção e ninguém percebe.

5. Se o tipo for o corpo de uma rota, acrescente o método ao `AgentdClient`
   (`packages/sdk/src/client.ts`) passando pelo `parseOrThrow`.

## Procedimento: mudar a versão do protocolo

`PROTOCOL_VERSION` aparece em três lugares, e os três precisam mudar juntos:

| Arquivo                                | Forma                               |
| -------------------------------------- | ----------------------------------- |
| `crates/agentd/src/api/types.rs`       | `pub const … : u32 = 1`             |
| `packages/schemas/src/api.ts`          | `export const PROTOCOL_VERSION = 1` |
| `apps/desktop/src-tauri/src/daemon.rs` | `pub const … : &str = "1"`          |

O valor do desktop é texto porque vai direto para o header. Não há como gerar
esses três a partir de um só hoje; o que existe é o teste de integração do daemon
que verifica o header em toda resposta, inclusive nas de erro.

## O que a validação não cobre

- **A ponte do Tauri não valida nada.** Ela repassa `serde_json::Value` de
  propósito (ver [architecture.md](architecture.md)); quem valida é o zod dentro
  do webview, em `apps/desktop/src/lib/bridge.ts`. Um `SchemaMismatchError` ali
  vira um estado `contract.mismatch` visível na tela, com o campo citado.
- **O schema não verifica semântica.** Ele garante que `vramTotalMb` é um inteiro
  ou `null`; não garante que o número faz sentido. Regras desse tipo pertencem ao
  Rust, onde o dado nasce.
- **Divergência de `serde` dentro de uma variante de enum passa despercebida até
  o `pnpm bindings`.** É o caso conhecido de `Event::DaemonStarted`, que emite
  `socket_path` em snake_case enquanto as outras variantes usam camelCase: falta
  o `rename_all` nessa variante. O schema zod espelha o que o Rust **de fato
  emite**, não o que ele deveria emitir. Quando o Rust for corrigido, o
  `assertSchemaMatches` quebra o typecheck — que é exatamente o comportamento
  desejado.

## Referência rápida

| Comando                             | O que faz                                                |
| ----------------------------------- | -------------------------------------------------------- |
| `pnpm bindings`                     | apaga e regenera `packages/schemas/src/generated/`       |
| `pnpm bindings:check`               | falha se as bindings commitadas estiverem defasadas      |
| `pnpm typecheck`                    | `tsc -b` em todos os pacotes; é onde as asserções falham |
| `pnpm --filter @elara/schemas test` | os testes de round-trip dos schemas                      |
